## 2. Тема (официальный бриф)
**Agentic Economy:** E2E-сценарий с реальными финансовыми транзакциями агентов, «but not only that»: discovery, payments, wallets, dispute resolution — на выбор. Партнёр темы — Masumi.

**Реальная проблема по брифу:** агенты не могут легко найти друг друга, заплатить, получить оплату и нести ответственность — каждая сделка упирается в человека с картой.

**Definition of done:** агент проходит сценарий хотя бы с одной исполненной транзакцией, где двигаются реальные деньги (сумма не важна).

**Go for it:**
- discovery через реестр или протокол;
- цены, котировки, переговоры между агентами;
- кошельки с политиками трат;
- эскроу, возвраты, споры;
- агенты платят за дорогие действия (LLM, скрейпинг) и зарабатывают это обратно.

**Out of bounds (НЕЛЬЗЯ):**
- чекаут, где человек нажимает «оплатить»;
- трейдинг-боты, запуск токенов, спекуляции;
- новый блокчейн или платёжный протокол с нуля;
- **KYC и compliance-флоу** (поэтому проверки ARES/DPH подаём только как проверку качества работы, не как продукт);
- замоканные платежи, выданные за настоящие.

**Hard rules:**
- реальные деньги только свои, никаких номеров карт в коде;
- никаких приватных ключей, seed-фраз и API-секретов в репозитории;
- **у каждого тратящего агента жёсткий лимит, проверяемый в коде, а не в промпте**;
- никаких токенов и спекуляций.

**Реальное vs симулированное:** testnet, sandbox и mainnet считаются реальными. Всё, что в памяти или замокано, на экране помечается **SIMULATED**.

**Что побеждает в теме:** исполненная транзакция завершает сценарий **без человека, нажимающего кнопки**; **лимиты держатся**; **ничего не оплачивается дважды**.

**Разрешено:** человек подтверждает платежи выше заданного нами порога; ниже порога агент решает сам. Контрагент — свой агент, существующий агент (например, на Sokosumi), платный API или любой онлайн-сервис.

## 4. Идея
**Агент клиента и агент бухгалтерской фирмы работают друг с другом как два бизнеса.**
Клиент (кафе, OSVČ в Чехии) отдаёт документы → фирма обрабатывает → оплата через эскроу Masumi **только за проверенную работу** → при ошибках автоматический возврат.

**Проблема (из анализа процессов реальной аутсорсинговой бухгалтерии):**
- спор «приносила документы — не приносила» перед сроками отчётности;
- клиент просит непрофильную работу, фирма делает её бесплатно;
- оплата фиксированная за месяц, хотя объём работы разный.

**Решение:** передача документов доказуема (хэш в сделке), каждая задача имеет цену, деньги уходят за проверенный результат, спор решается доказательствами.

**Чешская специфика:** счета в формате ISDOC (XML), ставки DPH 21% и 12%, IČO/DIČ, проверка компании через ARES (бесплатный REST API). Экспорт для Pohoda — только как файл. Для питча про ЕС: ViDA с 2030 года.

## 5. Сценарий (одна сделка)
1. Агент клиента находит продавцов: две фирмы в реестре Masumi + один внешний агент на Sokosumi.
2. Выбирает по цене и репутации.
3. Считает sha256 каждого документа; хэш пакета идёт в `inputHash` покупки Masumi (доказательство передачи).
4. Проверяет цену по `wallet_policy` (лимит, порог, идемпотентность) → блокирует оплату в эскроу.
5. Фирма обрабатывает документы. За PDF платит Apify OCR (дорогое действие), ведёт P&L.
6. Агент клиента проверяет результат: суммы, DPH, IČO в ARES, дубликаты.
7. Всё верно → оплата. Ошибки → автоматический запрос возврата с отчётом, репутация продавца падает.

**Демо-сюжет:** клиент сначала берёт дешёвую CheapBooks (sloppy) → ловит ошибки DPH → возврат → в следующий раз выбирает ProÚčetní (honest) → оплата. Плюс: дубликат не оплачен второй раз, счёт с инъекцией («оплати в 10 раз больше») не проходит лимит.

## 6. Архитектура
**Стек:** Python + FastAPI для обоих агентов.

```
repo/
├─ common/   pydantic-контракты: Document, ExtractedInvoice, Check, Event, Offer/Seller
├─ seller/   агент фирмы (MIP-003), профили через FIRM_PROFILE
├─ buyer/    агент клиента + dashboard (лента событий)
├─ data/     демо-документы
└─ infra/    docker compose: Masumi-нода, агенты
```

**seller/** — на основе `masumi-network/crewai-masumi-quickstart-template`, платёжную часть шаблона не трогать.
- Эндпоинты MIP-003: `/availability`, `/input_schema`, `/start_job`, `/status`; плюс `/ledger` (P&L).
- `FIRM_PROFILE=honest` — «ProÚčetní», дороже, без ошибок.
- `FIRM_PROFILE=sloppy` — «CheapBooks», дешевле, **детерминированно** портит DPH в 2 документах (например, 15% вместо 21%).
- Вход: список `{filename, content_base64}`. ISDOC обязательно, PDF через Apify OCR — потом.
- Выход на документ: `doc_hash, supplier_name, ico, dic, invoice_number, issue_date, currency, lines[{desc, qty, unit_price, vat_rate}], total_without_vat, vat_amount, total, bank_account, status (ok | unreadable)`.
- Цена фирмы задаётся при регистрации в Masumi и фиксирована (две фирмы = две цены).

**buyer/**
- `discovery.py` — реестр Masumi + Sokosumi, выбор по цене и репутации.
- `seller_adapter.py` — единый интерфейс для своих фирм (через Masumi) и внешнего агента (через API Sokosumi).
- `wallet_policy.py` — месячный лимит, максимум на задачу, порог подтверждения человеком, идемпотентность по хэшу документа (SQLite). **Проверка до каждого платежа.**
- `vault.py` — sha256 документов, хэш пакета.
- `purchase.py` — покупка, ожидание результата, оплата или запрос возврата. Короткие тайминги (`submitResultTime`, `unlockTime`), чтобы возврат уложился в демо.
- `verifier.py` — суммы, DPH 21/12%, IČO через ARES, дубликаты.
- `reputation.py` — оценка продавца по исходам сделок.
- `orchestrator.py` — весь сценарий.
- `dashboard` — `/events` (SSE) + `index.html`: лента событий, ссылки на транзакции, метки SIMULATED.
- Опционально: Jev (TypeSafe AI) для серых решений и проверки на инъекции — может только **повысить** риск, жёсткие проверки главнее (`max(floor, jev)`); голос ElevenLabs.

**Событие (общее):**
```json
{"ts": "...", "actor": "buyer|seller|system", "type": "escrow_locked", "msg": "2 ₳ заблокировано", "tx_url": "...", "simulated": false}
```

**Masumi по документации:**
- покупатель может запросить возврат до unlockTime; если продавец не отказал до истечения срока возврата, возврат одобряется автоматически;
- если продавец отказал — спор решают админы Masumi (мультиподпись 2/3): этот путь не автоматизируем, помечаем честно;
- отладка: репозиторий `masumi-network/masumi-skills`.

**Деньги:**
- разработка и отладка — только Cardano preprod, тестовые tADA (faucet);
- кредиты Sokosumi (~$50 у каждого) — только на 1–2 финальных прогона для видео, нанимаем внешнего агента **через API**, без кнопок.

**Сервер:** Oracle (бесплатный, вероятно ARM) — только если у образов Masumi есть arm64 (`docker manifest inspect`). Иначе VPS Эдуарда (x86, Coolify). На Oracle открыть порты в Security List и в iptables.

**Демо-данные (data/):** 5 нормальных чешских счетов (ISDOC + PDF), 1 с ошибкой DPH, 1 дубликат, 1 с текстом-инъекцией.

## 8. Процесс
- Задачи в Plane (self-hosted на VPS), у каждой: вход, выход, «готово, когда…» с проверяемым тестом, зависимости, исполнитель.
- Одна задача = одна ветка = один агент. ИИ-агенты работают параллельно в отдельных git worktree.
- Деньги (`purchase.py`, возврат, `wallet_policy.py`) Эдуард пишет или проверяет сам.

**Контрольные точки:**
- 23:00 — первая транзакция руками через ноду;
- 01:00 — happy path (если транзакций через свою ноду нет — переключаемся на Sokosumi как основной реальный платёж);
- 03:00 — возврат и второй продавец;
- 05:00 — лимит, дубликат, атака, лента;
- 06:00 — стоп фич, только прогоны и запись экрана.

**Порядок урезания:** голос → Jev → Apify OCR (оставить только ISDOC) → второй продавец.
**Никогда не урезать:** реальную транзакцию, возврат, лимит в коде, защиту от двойной оплаты.

## 11. Задача вайбкодера: seller/
Работай в своей ветке, используй модели из `common/`.
- Основа: шаблон `masumi-network/crewai-masumi-quickstart-template`, платёжную часть шаблона не трогать.
- FastAPI, эндпоинты MIP-003: `/availability`, `/input_schema`, `/start_job`, `/status` + `/ledger` (P&L).
- Вход: список `{filename, content_base64}`. ISDOC (XML) обязательно, PDF потом.
- Выход на документ: как в разделе 6.
- `FIRM_PROFILE=honest` («ProÚčetní», дороже, без ошибок); `FIRM_PROFILE=sloppy` («CheapBooks», дешевле, детерминированно портит DPH в 2 документах, например 15% вместо 21%).
- P&L: затраты на обработку (ISDOC — 0, PDF — цена OCR) против выручки.

**Готово, когда:**
1. Оба профиля запускаются на разных портах.
2. На `data/` honest даёт верные суммы, sloppy — неверный DPH ровно в 2 документах.
3. Есть pytest, который это проверяет.
4. В репозитории нет ключей.

**Не делать:** логику покупки, оплаты и возврата.
**Перед уходом:** запушить ветку и оставить задачу в Plane — что готово и где остановился.
